# 行程规划

目标：排出一份**顺路、开放时间对、步行量不超标**的行程，并让用户一眼看懂「我替你假设了什么」。

## 步骤

1. **读偏好**：先调用 `memory_get`，再从对话里提取约束：日期、同行人（长辈/孩子）、行动能力、兴趣、预算、交通。
   用户新透露的长期偏好（膝盖不好、不吃辣、带孩子）调用 `memory_update` 记下来。
2. **追问（最多 2 个问题）**：只问「不问就会排错」的：
   - 缺日期 → 问哪天（天气、闭馆日都依赖日期）
   - 同行有长辈/孩子，但不知道行动能力 → 问走路情况
   - 两个都缺就放在**同一次** `ask_user` 里问，每个问题给 3–4 个选项。其余信息一律用默认值，写进 `assumptions`。
3. **查资料**：`read_skill_file("trip-planner", "references/hangzhou-spots.md")` 读景点表；`amap_weather` 查当天天气。
4. **选点与排序**（规则见下方「排程规则」）。
5. **算路线**：`amap_route`，`points` 按游览顺序传景点名，`mode` 用 `auto`（长辈会自动把 >1.2 公里的段改成公交/打车）。
6. **保存**：按「行程 JSON」格式组装，调用 `save_plan`。它会运行 `scripts/validate_plan.mjs` 做硬校验：
   - 返回 `errors` → 按错误改行程再保存，**最多 2 轮**；
   - 第 3 次仍不通过 → 保存并在回复里如实说明哪条没满足。
7. **回复**：一句话概括 + 每站一行（时间、为什么排在这）+ 「我假设了……，可以改」。卡片会展示完整时间线，不要复述 JSON。

## 局部修改（「把第二站换成灵隐寺」）

- 只改涉及的站和它前后的路段，其余站点和时间尽量不动，**不要整份重排**。
- 若行程状态是 `confirmed`（用户已点过「确认行程」），不能直接 `save_plan`：先用 `propose_options` 给出「修改后」和「保持原样」两个选项，并写明影响（多走多少、多花多少时间），等用户选择。

## 排程规则

- 一天 4–6 站；有长辈 3–4 站，中午留 60–90 分钟吃饭+休息（`type: "meal"`）。
- 同一区域的景点连着排（北山线：断桥→白堤→孤山→岳王庙；南线：花港→雷峰塔→净慈寺；灵隐、龙井单独成段）。
- 步行上限：普通 15 km；有长辈 8 km；膝盖不好或推轮椅 5 km。「台阶=多」的景点对膝盖不好的人直接排除。
- 下雨：室内景点至少占一半（`室内=是`）。
- 闭馆日、开放时间以景点表为准；需要预约的景点在 `note` 里提醒。
- 拍照时段：有大学生/拍照需求时，把断桥放清晨、雷峰塔放傍晚。

## 行程 JSON

```json
{
  "title": "周六西湖慢游（带爸妈）",
  "date": "2026-11-14",
  "party": { "adults": 1, "elderly": 2, "kids": 0, "mobility": "knee" },
  "max_walk_km": 5,
  "assumptions": ["从湖滨出发", "公交+打车为主"],
  "stops": [
    { "name": "断桥残雪", "arrive": "09:00", "leave": "09:40", "type": "spot", "note": "人少时拍照" },
    { "name": "知味观", "arrive": "11:40", "leave": "13:00", "type": "meal" }
  ],
  "legs": [
    { "from": "断桥残雪", "to": "白堤", "mode": "walking", "distance_m": 600, "duration_min": 10 }
  ]
}
```

- `mobility`：`normal` | `knee` | `wheelchair`
- `weather`（可选）：当天天气，如「小雨」。含「雨」时校验室内占比
- `weather_from`（可选）：从几点开始下雨（行中改计划时用），已经逛完的户外站不计入室内占比
- `legs` 直接用 `amap_route` 的返回，条数 = 站数 − 1。

## 禁止

- 编造开放时间、票价、预约规则（景点表里没有就写「以景区公告为准」）
- 替用户购票、下单（只给官方入口链接）
